How it works

Real LLMs, running inside Internet Computer canisters — no off-chain API, fully verifiable.

In-canister LLMs

Each model is deployed as a smart contract using llama_cpp_canister (llama.cpp on the Internet Computer). The gguf weights are uploaded into the canister's stable memory, loaded into working memory, and inference runs on-chain. Because the Internet Computer caps the work per message, a reply is produced across a sequence of update calls — the app streams each batch of tokens to you as it arrives.

The studio

  • Model switch. Pick a model from the dropdown; each is a separate on-chain canister. Switching starts a fresh conversation.
  • System prompts. Use the default persona or open the editor to write and save your own prompt slots. The system prompt shapes every reply in a conversation.
  • Live stats. A conversation shows turns, in-canister calls, approximate tokens in/out, tok/s, and the exact cycle cost.

Exact cost & speed, measured in-canister

All inference is routed through a single controller canister (icgpt_admin), which is the only caller allowed to reach the model canisters. Because it is the sole caller, it measures each call precisely: it reads the model canister's live cycle balance right before and after the call (and brackets the IC system time) to report the exact cycle cost and exact tok/s — excluding network round-trips and the controller itself.

A worked example: the word-guessing game#

Here is a concrete on-chain AI task, and how ICGPT helps you optimize it. We want the model to run a word-guessing game: given a secret word, it must return one short hint that describes the thing — without ever writing the word itself. Keeping the secret is the whole game, so the model has to reliably obey a negation (“do not mention the word”).

The prompt design

All of the behaviour lives in the system prompt — no app code, just words. It states the rule and gives one worked example, so the model learns the shape of a good hint: 

You support a word-guessing game. When asked for a hint about a
word, give ONE short clue that describes what the thing IS or DOES,
using other words, without writing the word itself.

Example:
  Request: Provide a hint about CAT. Do not mention CAT.
  Hint: A small furry pet that purrs and loves to chase mice.

This prompt is saved once in the ⚙ System panel. Each turn of the game is then just a short request: 

Provide a hint about HOUSE. Do not mention HOUSE.

Qwen3-1.7B — keeps the secret

With the 1.7B model the hint is clean: it describes a house without ever saying the word.

ICGPT measured this exact turn, fully on-chain:

  • 1 turn — one request/response exchange.
  • 30 in-canister calls — the update calls needed to ingest the prompt and generate the hint.
  • ~95 in / ~15 out tokens — approximate prompt tokens ingested and hint tokens generated.
  • ~0.7 tok/s — measured generation speed.
  • 640.93B cycles (~$0.8524) — the exact cycle cost of this turn.

Qwen3-0.6B — leaks the secret, but is cheaper

The smaller 0.6B model gives the game away: its hint literally contains the word house.

  • 1 turn
  • 8 in-canister calls
  • ~95 in / ~14 out tokens
  • ~2.9 tok/s
  • 154.99B cycles (~$0.2061)

So the 0.6B is roughly 4× faster and ~4× cheaper — but it fails the task. Small models are weaker at following negations and keeping a secret: told “do not mention HOUSE,” the 0.6B reaches for the most obvious word anyway, while the 1.7B has enough capacity to hold the constraint and describe around it.

Why is the better model the more expensive one? It comes down to how many tokens each canister may generate per update call. The 1.7B model is capped at 4 tokens per update call, while the 0.6B can do 20 tokens per update call — both limits chosen to stay under the Internet Computer's per-message instruction limit. Producing the ~15-token hint therefore takes the 1.7B many more calls (hence 30 vs 8 in-canister calls, and the higher cost). Bigger model → fewer tokens per call → more calls → more cycles.

This is exactly why prompt optimization matters. The goal is to get the quality you need at the lowest on-chain cost — by choosing the right model, sharpening the system prompt, and tuning the parameters so a smaller, cheaper model can succeed where it otherwise would not.

Amortizing the system prompt

The numbers above include a one-time cost: those ~95 input tokens are almost entirely the system prompt, ingested on the first message of the conversation. In a real word-game app you pay that ingestion only once — it is cached in the model canister — and every following hint request is just a few tokens in and a few tokens out. So the steady-state cost per hint is much lower than this first turn suggests.

ICGPT's stats today report the cost of a whole turn. We are extending the metrics collection to break out one-time prompt ingestion from the recurring per-request cost, so you can investigate the true steady-state cycles cost of a repeating task like this one.

Isolation & concurrency

Every user's conversation lives in its own prompt-cache file inside the model canister, keyed by their principal — so no one can read or affect anyone else's chat. A single model canister serves many users by time-sharing one compute buffer, swapping each user's cache in and out per request. The design is safe under concurrency; the ceiling is throughput (one inference per model canister at a time).
