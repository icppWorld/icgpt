Prompt Cost Lab

The studio's default view — design a repeating on-chain AI task, sweep its variables, and read the exact cost per request and the quality, so you can optimize model, prompt, and parameters together.

Chat is great for exploring one conversation. The Prompt Cost Lab is for the real engineering question behind a production on-chain task: what does it cost to run this prompt a thousand times, and does it stay correct? The Lab answers both, measured on-chain, with no guesswork.

Templated prompts & variable sweeps

A task is a template with two parts and any number of variables:

  • System template — the fixed instructions. This is the cached prefix: it is ingested once and reused for free on every following request, so keep the swept {{variables}} out of it.
  • User template — the per-request prompt. Put the swept {{variables}} here, as late as possible.
  • Variables — each is either a sweep (a list of values, one trial per value) or a constant. Every combination of sweep values becomes one trial, and the Lab runs them all.

So a word-guessing template with a {{word}} sweep of HOUSE, TREE, CAR, OCEAN, GUITAR runs the same task five times and reports the cost and quality of each.

Exact cost, split the way it actually bills

The Lab separates the two costs that matter for a repeating task, both measured exactly on-chain:

  • One-time warm-up — ingesting the fixed system prefix. You pay this once; afterwards it is served from the model canister's prompt cache.
  • Steady-state per request — the recurring cost of one call after the prefix is warm: the re-ingested suffix plus the generated tokens. This is the number that multiplies when your task runs at scale (the Lab also shows it as $ / 1k requests).

The cache-break analyzer uses the model's exact token accounting to show how many prompt tokens are reused from the cache for free versus re-ingested on every call. The guidance is concrete: move swept variables later in the prompt to shrink the re-ingested suffix, and watch the steady-state cost drop.

Quality rules — is it still correct?

Cheap is worthless if the answer is wrong, so each trial is scored against the rules you define, and the Lab reports a pass-rate:

  • Reply must / must not contain a string (great for negation tasks — e.g. the hint must not contain the secret word).
  • Reply must match a regex (case-insensitive).
  • LLM judge — a rubric is scored 0–100 by an on-chain judge model (DFINITY's Qwen3-32B), and the trial passes if the score clears your threshold.
  • Manual — you rate each reply pass/fail yourself.

Compare runs (A/B)

Change one thing — a different model, a sharper system prompt, a lower temperature — run it again, and the Compare runs table lines the runs up side by side: one-time cost, steady $/req, $/1k, and pass-rate. This is how you find the cheapest configuration that still passes: often a smaller model with a better prompt beats a bigger one.

Everything you can vary

  • Model — any of the five on-chain models, from Gemma-3-270M to Qwen3-1.7B.
  • Parameters — temperature, sampling cut-offs, penalties, response length, thinking, seed. See Parameters.
  • Samples per trial — run each trial several times and average, so a noisy result doesn't fool you.
  • Custom templates — save your task into one of three Custom slots (kept per browser) and load it back later.
Runs keep going while you look around. An experiment lives at the app level, not on the page — so you can switch to Chat or the Canisters page mid-run and come back to find it still going (a Lab running indicator shows in the top nav). Only a full page reload stops it.
